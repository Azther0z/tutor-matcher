# Project Structure Review

Findings from reviewing the current repository state. Items are grouped by severity.

> **Historical snapshot:** This review records an earlier repository state and is not the
> current implementation checklist. The repository now has root onboarding documentation,
> backend ESLint, Jest/Supertest tests, and a Cucumber.js Gherkin suite. See
> [Project Architecture](project-architecture.md) and [Testing](testing.md) for the current
> baseline. The original findings below remain unchanged as historical review evidence.

---

## Critical — Will Cause Bugs or Broken Dev Setup

### 1. `db.ts` uses `pg` Pool while Prisma is installed — pick one

`src/lib/db.ts` creates a raw `pg.Pool`. Prisma is also installed and its client is generated into `src/generated/prisma`. Having both active means queries will be split across two connection pools with no consistency guarantee.

**Fix:** Remove the `pg` pool and use the Prisma client everywhere. Delete `db.ts`, create `src/lib/prisma.ts` that exports a singleton `PrismaClient`.

```ts
// src/lib/prisma.ts
import { PrismaClient } from "../generated/prisma";

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient };

export const prisma = globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```

If raw SQL is needed for stored proc calls, use Prisma's `$queryRaw` / `$executeRaw` — no need for a separate `pg` pool.

---

### 2. Frontend has no way to reach the backend

There is no `NEXT_PUBLIC_API_URL` (or equivalent) configured anywhere in the frontend. When the browser makes fetch calls to Express, it needs an explicit base URL. Without it, every API call will either hardcode `localhost:3001` or silently fail.

**Fix:** Add `apps/frontend/.env.local.example`:

```env
NEXT_PUBLIC_API_URL=http://localhost:3001
```

And document that developers must copy it to `.env.local` after cloning.

---

### 3. Prisma schema has no models and no datasource URL

`apps/backend/prisma/schema.prisma` is empty (just the generated boilerplate). The datasource `url` is in `prisma.config.ts`, not the schema — which is correct for Prisma 7, but **no models have been defined yet**. No `prisma generate` can succeed, meaning `@prisma/client` cannot be imported at all.

**Fix:** Translate the schema in `docs/project-schema.md` into Prisma models. This is the most blocking piece of missing work.

---

### 4. No `prisma generate` step after install

The generated Prisma client goes to `src/generated/prisma/` which is `.gitignore`'d. Anyone who clones the repo and runs `npm install` will get broken imports until they manually run `npx prisma generate`.

**Fix:** Add a `postinstall` script in `apps/backend/package.json`:

```json
"postinstall": "prisma generate"
```

## Important — Quality and Correctness

### 5. `prisma` CLI is in `dependencies`, not `devDependencies`

The `prisma` package (CLI) is a build tool, not a runtime dependency. Only `@prisma/client` belongs in `dependencies`.

**Fix:**

```bash
npm install -D prisma
npm install @prisma/client
```

---

### 6. `pg` and `@types/pg` can be removed

Once Prisma is used exclusively (see item 1), the `pg` and `@types/pg` packages are dead weight. Prisma manages its own connection internally.

---

### 7. No global error handler in Express

`app.ts` has no error-handling middleware. Express 5 changed how async errors are handled — unhandled promise rejections are now forwarded automatically, but without a registered error handler, the default behaviour sends a plain HTML 500 page instead of JSON.

**Fix:** Add before `export default app`:

```ts
import { Request, Response, NextFunction } from "express";

app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
  console.error(err);
  res.status(500).json({ error: err.message || "Internal server error" });
});
```

---

### 8. Backend `tsconfig.json` does not include Jest types

`@types/jest` is installed but `tsconfig.json` has no `"types"` field, so TypeScript inside test files may not resolve `describe`, `it`, `expect` without the `@swc/jest` transformer carrying them. Add this to avoid IDE errors in test files:

```json
"types": ["jest", "node"]
```

Or create a separate `tsconfig.test.json` that extends the base and adds `@types/jest`.

### 10. `.gitkeep` files remain in non-empty directories

`src/lib/` now has `db.ts` alongside `.gitkeep`. Once a directory has real files, `.gitkeep` should be removed.

**Affected:** `src/lib/.gitkeep` (has `db.ts`). The others (`controllers/`, `middleware/`, `routes/`) are still empty — keep those until real files are added.

---

### 11. Root `package.json` has unnecessary fields

`"main": "index.js"` and `"directories": { "doc": "docs" }` were generated by `npm init` and have no meaning for a monorepo root.

## Recommended Additions

### 12. Add `.env.local.example` for the frontend

Document required frontend env vars so new developers know what to set up. Minimum:

```env
# apps/frontend/.env.local.example
NEXT_PUBLIC_API_URL=http://localhost:3001
```

---

### 13. Add ESLint to the backend

The frontend has ESLint (via Next.js). The backend has none. Inconsistent linting rules across the monorepo will cause style drift.

**Fix:**

```bash
cd apps/backend
npm install -D eslint @typescript-eslint/parser @typescript-eslint/eslint-plugin
```

Create `apps/backend/.eslintrc.json`:

```json
{
  "parser": "@typescript-eslint/parser",
  "plugins": ["@typescript-eslint"],
  "extends": ["eslint:recommended", "plugin:@typescript-eslint/recommended"]
}
```

---

### 14. Add Husky + lint-staged

Without a pre-commit hook, Prettier and ESLint only run if developers remember to. Husky + lint-staged enforces formatting on every commit.

```bash
npm install -D husky lint-staged   # at repo root
npx husky init
```

`package.json` addition:

```json
"lint-staged": {
  "apps/**/*.{ts,tsx}": ["prettier --write", "eslint --fix"],
  "apps/**/*.{json,css,md}": ["prettier --write"]
}
```

---

### 15. Add a health check to the Postgres service in docker-compose

Without a health check, Express may start before Postgres is ready and fail its first connection.

```yaml
services:
  postgres:
    ...
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
```

---

### 16. Document the post-clone setup steps

There is no top-level `README.md` or setup guide. New team members need to know:

1. Copy `apps/backend/.env.example` → `apps/backend/.env`
2. Copy `apps/frontend/.env.local.example` → `apps/frontend/.env.local`
3. `docker-compose up -d`
4. `cd apps/backend && npm install` (runs `prisma generate` via postinstall)
5. `npx prisma migrate dev` (applies migrations)
6. `npm run dev` in both `apps/backend` and `apps/frontend`
